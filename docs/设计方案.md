## 2. 技术选型（决策表）

| # | 决策 | 结论 | 依据 |

## 3. 架构设计

### 3.1 模块划分（7 个 Gradle 模块）

```
:app        Activity/Fragment/列表/编辑器/DI 装配（ServiceLocator）
:core       纯 Kotlin 零 Android 依赖：model（Script/Step/Caps）+ compiler（Script→Timeline）
            + runtime（PlaybackClock/Scheduler/状态机/RDP/手势分段器）
:inject     InputBackend 接口 + A11yBackend + RootBackend + BackendSupervisor
:capture    CaptureBackend：MotionEvents(API34+) / OverlayCapture(<34) / EvdevCapture(root)
:platform   AccessibilityService、RootFgs、BootReceiver、Watchdog、通知
:overlay    悬浮窗（Views + WindowManager）
:native     (v2 预留) uinput 写入器 / evdev 读取器
```

`:core` 零 Android 依赖是硬约束——它是唯一可 JVM 单测覆盖的部分，也是回放正确性的唯一保险。

### 3.2 运行时拓扑

```
App Process（单进程）
├─ Activity（列表/编辑/诊断）
├─ Overlay 悬浮窗（播放/暂停/停止/循环计数）
├─ AccessibilityService ── 常驻锚点，持有 Runtime
├─ RootFgs（仅 root 模式）── foregroundServiceType=specialUse
├─ BackendSupervisor ── 健康心跳（ALIVE/DEAD）
├─ PlaybackEngine ── 独占线程 + 绝对时限 park，循环体零分配
└─ RootBridge ── 常驻 su shell（stdin 流式下发）
```

**铁律**：回放引擎单实例 + 单 runToken。悬浮窗/通知/Activity 三方只能投递 Command（Start/Pause/Stop/SetLoop），禁止直接驱动引擎——这是同类 App 最常见的线上事故（重复点击）。

### 3.3 注入引擎抽象（批式，非事件式）

核心洞察：无障碍必须批处理，root 适合连续流，用「时间片」统一：

```kotlin
interface InputBackend {
    val caps: Caps                      // maxStrokesPerBatch/maxBatchDurationMs/maxSliceMs/latencyClass
    suspend fun prepare(): Result<Unit>
    suspend fun execute(slice: Slice): Result<Unit>   // 阻塞到片尾，绝不提前返回
    fun health(): Health                // Alive/Dead
}
```

调度器只面向 Slice：按 caps 把 Timeline 切成 ≤20 指且 ≤60s 的片，再用 `maxSliceMs`（400ms）压出命令消费点。片是**串行**派的：一次 dispatch 只承载一次按压，等回调（`onCompleted`/`onCancelled`）才发下一批，绝不预派发——新 dispatch 会取消在途手势。

### 3.4 A11y 后端（默认通道）

机制事实（AOSP main 源码级结论）：

| 约束 | 值 | 说明 |
|---|---|---|
| 单 gesture stroke 数上限 | **20**（`MAX_STROKE_COUNT`） | 超出抛 IllegalStateException |
| 单 gesture 总时长上限 | **60 000ms**（`MAX_GESTURE_DURATION_MS`） | 只影响长按/拖拽，不影响连点 |
| 采样步长 | targetSdk≥30 时 `1000/refreshRate` | 60Hz≈16ms，120Hz≈8ms，不可配置 |
| **新 dispatch 取消在途手势** | 是 | 一次新 dispatch 会取消上次手势及真实用户手势 → **不可流水线并发，必须等回调（onCompleted/onCancelled）再发下一批** |
| 息屏 | **不可用** | `PhoneWindowManager.shouldDispatchInputWhenNonInteractive` 在 STATE_OFF 直接吞事件；亮屏+锁屏未遮挡可送达 |
| 事件特征 | `FLAG_IS_ACCESSIBILITY_EVENT` + 虚拟 deviceId | 落点=屏幕绝对像素；宿主 App 可识别注入事件 |
| 状态栏/导航栏/IME | 机制可达，无官方保证 | dispatchGesture 只有 displayId 无 window 参数，落点由最顶层窗口决定 |

设计结论：
- **一次按压一次 dispatch**：`GestureDescription` 的多条 stroke 是同一手势的多根手指，只有时间上重叠的笔画才允许同批。早期按「一次塞 ≤20 个 tap、各自 offset」实现，实测 40 次相邻点击只生效 1 次（接收方看到的是同一根手指一直按着）；改为按按压分批后逐次准确。相邻两次按压的起点间隔由后端兜住 50ms 下限（片内 `GestureBatching` 整体后移，片间 `dispatchBatch` 补足）。
- 取消语义（第十七轮实测）：系统 `MotionEventInjector` 收到真实输入事件即作废在途手势并回调 `onCancelled`——这一笔丢掉、按绝对时间轴继续，**不算失败**（落点与代价见 `A11yBackend` 类注释）。没有降级链：失败即中止整轮并上报（引擎留游标供诊断页看，不自动续播），停因只有后端解绑、屏幕尺寸变化、`dispatchGesture` 返回 false、回调超时（片尾 +1.5s）。
- 用户必须手动开启无障碍（系统强制，无绕过）。

### 3.5 Root 后端（v1.1 范围，v1.0 不实现）

**修正点**：app 进程（untrusted_app 域）直接 `FileOutputStream("/dev/uinput")` 会被 SELinux enforcing 拒绝，`chmod 666` 无效。root 注入必须发生在 su 域。因此：

| 方案 | 延迟 | 实现量 | 结论 |
|---|---|---|---|
| 常驻 su shell + `input motionevent` 流 | 中低 | ~150 行 Kotlin | **v1.x 采用**。`input` 现运行在 system_server 内（非 fork app_process），单进程流式下发规避每条命令的进程启动开销 |
| `input tap/swipe/keyevent --async` | 高/低 | 零 | 兜底。注意 `input tap` 的 DOWN/UP eventTime 相同→按下时长≈0，**长按必须用 `input swipe x y x y <duration>`**；高频按键必须 `--async` |
| 直写 `/dev/input/eventX`（复用单 fd） | 最低 | 中 | 兼容性差（节点号/ABS_MT 协议每机型不同，社区实测约 1/1000 事件损坏），不做 |
| `/dev/uinput` 自建虚拟设备 | 最低 | 高（NDK 守护进程，Snagput 架构） | **v2**。需先装 NDK；仅在实测 SELinux 放行或需 <1ms 抖动时启动 |

su 会话缓存：`ProcessBuilder("su")` 常驻，stdin 写命令/stdout 读结果，禁止每条命令 `Runtime.exec("su -c ...")`。

### 3.6 录制模型

| 通道 | 版本 | 精度/体验 |
|---|---|---|
| `FLAG_SEND_MOTION_EVENTS` + onMotionEvent | API 34+ | 非阻塞、全保真，最佳 |
| 透明全屏 `TYPE_ACCESSIBILITY_OVERLAY` 阻塞采 | < 34 | 录制期遮挡底层，须明示 |
| root 读 `/dev/input/eventX` | root | 全保真，需 getevent 探测设备 |

### 3.7 脚本格式（文件即脚本，`files/scripts/<id>.json`）

```json
{
  "v": 1, "id": "s_01H...", "name": "每日签到",
  "screen": { "w": 1080, "h": 2400, "dpi": 420, "rot": 0 },
  "steps": [
    { "t": "tap",   "p": [[0.5, 0.62]], "d": 60 },
    { "t": "swipe", "p": [[0.5,0.8],[0.5,0.2]], "d": 320 },
    { "t": "multi", "p": [[[0.3,0.5],[0.3,0.1]],[[0.7,0.5],[0.7,0.1]]], "d": 400 },
    { "t": "delay", "d": 1000 },
    { "t": "loop",  "n": 0, "body": [] }
  ]
}
```

要点：
- **坐标归一化到 [0,1]**，录制时记录分辨率/旋转；当前屏幕与录制时不一致（方向、旋转、宽高比 >8%、dp 视口 >8%）**拒绝播放并说明差异**（`ScreenMetrics.mismatchOf`），不静默点错位置。
- **语义步骤**（按下→抬起 <150ms 且位移 <8dp = tap；1 指移动 = swipe；≥2 指 = multi），RDP（容差 1px）简化路径。体积比原始事件流小 1–2 个数量级且用户可编辑。
- **动作延迟**（pd）：每个动作类步骤按下前的时间空白；`pd = -1` 表示跟随脚本的默认动作延迟（ad）。pd 与 d（按压时长）都进时间轴，因此「等 100ms 再点 60ms」在编译期就确定为 160ms 的拍距。
- 循环用嵌套 `loop.body`，无配对错误；单步重复用 `repeat`（编译期按次数展开，与脚本级循环在产物上无区别）。
- 编译期展开为 Timeline（预计算 startOffsetMs），运行期零分配；时钟统一 `System.nanoTime()`，**绝对时限 park（`LockSupport.parkNanos`）**，不用协程 `delay()`（5–15ms 抖动不可接受）；pause/resume 用时间基准平移。

## 4. 保活架构

### 4.1 结论：单进程 + 无障碍服务作锚点

- AOSP 官方文档明确：**无障碍服务使应用处于活跃进程状态、不受 App Standby 影响**（与前台服务同级）。这是最强锚点且功能必需，零额外成本。
- root 模式用 FGS：`foregroundServiceType="specialUse"` + `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`（A14+ 不声明类型 `startForeground` 直接崩；`dataSync` 有 6h/24h 硬顶、`shortService` 不支持 sticky、`mediaPlayback` 语义不符）。
- **不做**双进程互拉、1px Activity、无声音频、JobScheduler 高频轮询——Android 8+ 全部失效，纯负收益。

### 4.2 保活组合拳（按收益排序）

1. 无障碍服务常驻（最强锚点）
2. 悬浮窗权限 `SYSTEM_ALERT_WINDOW`（功能需要，顺带大幅降低被杀概率）
3. 电池优化白名单引导（`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`）
4. `START_STICKY` + `onTaskRemoved` 重挂
5. `setExactAndAllowWhileIdle` 低频自检（5–15min，只做健康检查/重挂）
6. `BOOT_COMPLETED` 恢复 root 服务（无障碍由系统自恢复）
7. 播放期 `PARTIAL_WAKE_LOCK` + 悬浮窗 `FLAG_KEEP_SCREEN_ON`，用完立即释放

**期望校准（重要）**：电池白名单只解锁"网络 + partial wake lock"，**不解除 Alarm/Job 推迟**；Alarm 在 A12+ 最小窗口 10min 且 Doze 下全部推迟，`SCHEDULE_EXACT_ALARM` 需用户授权。Alarm/Job/WorkManager 只能做"把用户拉回来"的低频兜底，**不能承担点击节拍**；节拍只靠常驻服务 + 自有时钟。

### 4.3 国产 ROM 引导（内置图文 + 自检按钮）

| ROM | 用户侧设置 |
|---|---|
| 小米 | 自启动开 + 省电策略无限制 + 任务卡片上锁（`am_kill` 日志可查杀因） |
| 华为/荣耀 | 应用启动管理改手动（自启动/关联启动/后台活动全开） |
| OPPO/一加/realme | 允许后台运行 + 允许自启动 + 关智能省电 |
| vivo | 自启动 + **允许后台高耗电**（否则 App 外弹窗被拦） |
| 三星 | 从"休眠应用"移除 |

加**自检按钮**：写时间戳→用户切走 3 分钟→回来实测是否被杀，比任何文字都有效。产品文案明确告知"无 100% 保活"。

## 7. 里程碑与验证

**M0 骨架（3–4 天）**：仓库 + GPL-3.0 + 双远程（Gitee 主 / GitHub 备，同名 `autotap`）+ 日期版本号 + CI 体积门禁 + 空壳装机。验证：`assembleRelease` <1MB、`adb install` 成功、签名用本机密钥库（口令见同目录口令文件，不入库））。

**M1 回放内核（1 周，最高风险前置）**：`:core` 全 JVM 单测（循环嵌套/暂停续播/切片边界）+ FakeBackend 断言时序 p95 <3ms。**同点 100 连击在真机验证是否退化为长按（R9）**。此步必须先于 UI。
